# 服务重启与能力清单

Totemora 的产品定位是**常驻专业助手与多渠道消息沟通服务**：持续处理明确委托，结合项目背景筛选信息，给出有证据的行动建议，并通过合适的渠道传递结果、接收反馈。首个完整流程是“项目情报 → 行动建议 → 采纳或忽略 → Lifeline 交接草稿”。

Gateway 持有业务状态、项目判断、建议和用户决定；Notifier 持有通知目标、投递重试和逐目标回执。Telegram 的双向命令由 Gateway 处理。多 Agent、预算、验收和资产授权继续作为内部能力，下一阶段优先验证具体服务的价值。

## 生态职责

| 组件 | 负责什么 | 当前接入边界 |
| --- | --- | --- |
| Totemora | 持续关注项目、整理证据、提出建议、记录采纳、组织消息交互 | 本轮先贯通情报与行动建议 |
| EchoMe | 项目背景、约束、历史经验 | 当前项目卡仍由操作员维护；尚未自动同步记忆 |
| Lifeline | 正式目标、任务、阶段、排期与验收 | 当前只输出未提交草稿，真实项目与阶段映射待确认 |
| 开发 Agent | 执行已明确的调查、编码和测试任务 | 采纳建议不会自动启动 Agent 或执行命令 |
| LogWood | 可复用的实践与知识成果 | 行动结论尚未自动写入 |
| Notifier | 跨项目消息接入、领域路由、各通道发送及回执 | 独立服务，Gateway 通过 HTTP 使用 |

真实数据副本抽查还发现 RSS 采集历史只保留标题、URL 和日期，缺少来源摘要。最近 39 条候选中，30 条因此进入待核实；关联 ID、URL 和存储大小正常。本轮已提取 RSS 解析模块，保存来源实际提供的 `description` 或 `content:encoded`，清理 HTML 与控制字符，限制为 1,200 字符；仅含 Comments、链接列表等导航内容的条目仍无证据。缺失的历史正文无法离线恢复，也不能用模型生成摘要回填。规则关注词应使用原文中可出现的短词或明确短语，目标描述另存于项目目标；新版默认卡据此调整，已保存的用户项目卡保留原值。

真实副本还暴露了首页的历史读取瓶颈：界面只显示最近 4 条简报，原接口却返回 AI 6,668 条、财经 3,384 条，合计约 183 MiB；登录后刷新又重复请求。新版首页显式使用 `GET /api/intelligence?limit=4` 和 `GET /api/finance?limit=4`，在 SQL 中按创建时间取最近记录，再解析正文。`limit` 只接受 1–100 的整数；未带参数的既有接口和内部调用保持原有语义。证据面板的累计来源统计改为 SQLite 聚合，只返回计数；仍统计全部历史，不删除记录或缩短统计窗口。

## 受阻任务的处理方式

优惠来源使用稳定的“访问受阻”分类，`GET /api/deals/status` 的 `source_health` 提供 `blocked` / `backoff` 与 `retry_after`。明确失败按 5、10、20、40、60 分钟退避，最多一小时；每分钟的调度检查不会在等待期间再次抓取或重复记录同一失败。跨域验证页面不能靠扩大重定向范围解决。

转发来源将证书、TLS 握手、认证、配置、暂时不可用和响应格式错误分别归类，`GET /api/forwarded/status` 的 `polling` 提供 `failure_kind`、`consecutive_failures` 和 `next_poll_at`。一般失败从 5 分钟开始退避；证书、认证和配置失败从 30 分钟开始，上限 6 小时，重启后仍保留等待时间。来源受阻期间，已入库的待发送事件仍可按投递规则处理。

这些补丁解决重复失败造成的请求和日志堆积，不表示两个外部来源已恢复。未知投递结果仍保持 `uncertain`，不能通过换幂等键自动重发。排查文档与状态响应只保留脱敏分类，不公开上游私有地址、网络路由细节或凭据。

## 启用与验收顺序

1. 升级前取得 Gateway SQLite 一致性备份；Notifier 的数据库及私有配置独立备份。不要只复制仍有活动 WAL 的 `.db` 文件。
2. 新版 Gateway 启动时顺序执行 migration 019。它新增行动建议与决定账本、引用约束和索引，保留旧候选、评估与摘要；不会一次性把所有历史消息转换成行动。
3. 在“项目情报雷达”维护实际活跃项目，把模式设为 `shadow`。无 Jev key 时使用规则匹配，默认信心为 `null`，不消耗模型 Token；手动评估只生成记录与建议。
4. 审阅来源、项目相关性、下一步和验收依据，采纳或忽略建议。采纳只改变建议状态。查看或复制 Lifeline 草稿时，确认 `submitted:false`，再补充真实项目与阶段映射。
5. 确认摘要预览和现有通知目标后，选择 `active` 启用每日自动摘要。建议试运行先限制为 3 条，没有合格内容就不发送。
6. 单独核对 Telegram Bot 条件后使用 `/radar`；这会按显式请求回复消息，即使雷达处于 `shadow`。未配置通知目标、真实模型未调用或来源仍被阻断时，在验收记录中保留相应限制。

完整字段、API、模式和命令见[项目情报雷达](project-radar.md)；通知配置与诊断见[统一通知平台](notification-platform.md)。只读检查可使用：

```bash
bun run deals status
bun run forwarded status
bun run notifier:doctor status
bun run notifier:doctor targets
```

试运行两周主要记录：建议采纳数、采纳后的实际任务结果、重要变化漏选、重复信息与模型用量。发送条数和服务运行时长只作运行指标；成员人格成长、通用编排和新增资讯频道暂不作为本轮扩展重点。
