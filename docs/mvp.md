# Totemora 核心验证基线

本文件保留 MVP 的核心证明标准，不再充当当前功能清单。当前工程已经越过早期只读原型，实际进度见 [execution-plan.md](execution-plan.md)，当前能力见 [README.md](README.md)。

## 要验证的命题

**在有限智能预算下，可解释的异构成员派工是否比固定使用某一个模型更有效。**

界面、成员人格、专业服务和 Skill 治理都必须最终服务于这个命题；功能数量不是成功指标。

## 已具备的实验基础

- GPT、DeepSeek、Qwen、MiMo 成员与动态 Chief；
- 受限 Workspace、Task Analyzer、预算参数和候选排序证据；
- Mission、Run、成员/Skill 版本、调用量、失败归因与验收 Trace；
- 三策略 benchmark 烟雾入口；
- Git Flow、听风和内容工坊的真实专业任务及用户反馈；
- SQLite 持久任务、动作幂等、重启恢复和证据台。

## 仍需补齐的证明

- 10–20 个可重复真实任务，而不是少量示例；
- 单强模型、固定廉价模型和 Totemora 使用相同上下文与验收标准；
- 可追溯的模型价格/额度快照；
- 验收通过率、强模型 Token、总 Token、费用、时延、重试和失败归因汇总；
- Reviewer 与执行者分离，评价器自身偏差可检查；
- 对 Skill 版本和成员成长做升级前后对照，而不是只记录“已批准”。

## 通过标准

至少满足一项，并在多次任务中稳定复现：

1. 在质量可接受的情况下减少强模型 Token 或总成本；
2. 在相同预算下提高验收通过率；
3. 专业服务通过持久状态、确定性资产和经验复用，显著降低重复失败或人工介入。

所有结果都必须回答：选了谁、为什么选、使用哪个 Skill/资产版本、花费多少、谁验收、失败属于成员还是系统，以及下一次为何可能更好。

## 不可用来证明成功的信号

- 调用了更多模型；
- 生成了更多人格描述或文章；
- 扫描成功次数、通知送达次数或模型自评；
- 只在一个任务上优于基线；
- 没有固定版本、digest 和验收证据的“成长”。

若基线实验不能证明稳定收益，应暂停市场、更多成员和更复杂基础设施，优先修正派工、Skill、资产或验收模型。
